# Webapp Template — Hermes SDLC Rules

## Specification

- This repository uses GitHub Spec Kit (`.specify/`, `.agents/`, and `specs/`). Specifications remain the source of truth; Kanban cards are the durable execution and handoff layer.
- New features require `specs/<NNN-feature>/spec.md`, `plan.md`, and `tasks.md`, based on `.specify/templates/`. Reuse or update an existing feature directory when it already owns the scope.
- Before finalizing the specification, Planner performs a clarification pass. Separate resolvable implementation details from decisions that materially affect user behavior, security/privacy, data contracts, compatibility, scope, or irreversible architecture.
- For material unresolved decisions, Planner records them in the feature's `clarify.md` (when the feature directory exists), blocks the root card with `kind=needs_input`, and asks at most three focused questions at once. Each question includes a recommended option, alternatives, and consequences. Planner must not complete the root until answers are incorporated into `spec.md`, `plan.md`, `tasks.md`, and the Kanban graph.
- Auto-decomposed child cards remain provisional and dependency-gated while clarification is pending. Do not dispatch implementation based on unresolved assumptions.
- Acceptance criteria must be observable and mapped to tests or explicit manual verification.

## Agent pipeline

1. `planner` receives the triage root. Auto-decompose may already have created a provisional child graph. Planner creates/updates Spec Kit artifacts, inspects and corrects the existing graph, adds only missing cards or links, and never duplicates auto-created children. Planner completes the root only when the specification and graph agree.
2. `implementer` develops in an isolated worktree, creates a clean conventional commit, pushes the task branch, opens a GitHub PR against `main`, and requests same-card review from `reviewer` with the PR URL and exact head SHA.
3. `reviewer` reviews that exact PR head, requests changes or approves the implementation, and records the reviewed SHA.
4. A dependent `qa` card checks out/verifies the exact reviewed PR head, performs final acceptance and full validation, and records the QA-approved SHA. QA does not modify product code or merge.
5. A dependent `[DELIVERY]` card assigned to `integrator` verifies that the PR head still equals the reviewed and QA-approved SHA, verifies required GitHub checks, squash-merges the PR into remote `main`, deletes the remote task branch, and reads back the merged PR state and merge SHA.
6. `qwenfallback` is exception-only after an explicit hosted-model refusal and approval; it is not a general-purpose shortcut.

Kanban phase cards use `done` to release dependent phases. Therefore implementation/review and QA cards may be Done before deployment integration. Only a `[DELIVERY]` card in Done is evidence that the corresponding change is merged into remote `main`; feature-level reporting must not call the work delivered before that card completes.

## Validation

- During implementation: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\validate.ps1 precommit`.
- Before review: run the same command with `prepush`.
- Final QA: run the same command with `full`.
- Never use `QUALITY_THRESHOLDS_BYPASS=1` in agent validation.
- `full` includes type checks, lint/format, dependency architecture, duplication thresholds, Python/Go complexity and quality, Semgrep, runtime credential/logging/encoding/template/spec checks, tests, supply-chain/dependency audits, and Playwright E2E when present. Report required checks that were skipped because tooling was unavailable.

## Durable documentation

- Kanban is the execution log, not the sole home of long-lived knowledge. When a result will matter after the card is archived, document it in version control and link the path from the Kanban handoff and PR.
- Feature-specific requirements, clarification decisions, research, design rationale, contracts, rollout notes, findings, and verification evidence belong under the owning `specs/<NNN-feature>/` directory. Reuse established names such as `clarify.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `findings.md`, or `remediation-evidence.md` where appropriate.
- Cross-cutting architecture, operator runbooks, deployment procedures, troubleshooting, and user/developer guidance belong under `docs/` or the nearest component `README.md`.
- Security findings, remediation decisions, residual risks, and approved exceptions belong in `docs/security/` or the owning security specification. Never commit secrets, credentials, raw sensitive production data, or unnecessarily weaponized exploit material; use a minimal safe regression test or private task attachment when public repository documentation would create avoidable risk.
- Documentation is normally required for behavior or contract changes, non-obvious architectural decisions, migrations, operational procedures, security findings/exceptions, important QA discoveries, known limitations, and decisions future maintainers would otherwise have to rediscover.
- Do not commit transient logs, routine status narration, duplicated Kanban comments, or obvious descriptions of self-explanatory code. Store raw evidence as task/CI artifacts and commit only the durable conclusion and reproducible procedure.
- Every implementation, review, and QA handoff must list documentation paths changed, or state `No durable documentation needed` with a concrete reason. Reviewer verifies documentation accuracy; QA verifies user/operator-facing documentation against actual behavior.

## Human decisions

- If a material decision cannot be derived safely from the specification, do not guess and do not keep the worker session open waiting.
- Call `kanban_block` with kind `needs_input`. State one concrete question, why it blocks progress, the available options (recommended option first), and the consequence of each option.
- The user answers by adding a comment to the card and unblocking it. On redispatch, read the full comment thread and continue from the appropriate implementation or review phase.
- Use `capability` rather than `needs_input` only for an actual tool/model capability problem. Prefix genuine hosted-model refusals with `HOSTED_MODEL_REFUSAL:`.

## Handoffs

Every handoff must state changed files, exact verification commands, pass/fail/skip details, artifacts, and residual risks.
